# HCL Pure

## The substrate that came before Marvosa

**Grand Unified Harmonic Computational Language** — a pure-integer computational substrate where values carry phase and amplitude, constants are derived instead of imported, and every operation leaves a reversible braid-word trace.

[Marvosa](https://github.com/Ajordon30005/marvosa) came later. It incorporated hcl-pure into a larger system of memory, language, learning, persistence, and model hosting. This repository is the original substrate: the part that came first, and the part that makes the later composition possible.

> **Python is the shell. GUHCT is the arithmetic. Four parameters are the axioms. Everything else is derived. The braid word is the quantum state.**

## The idea in one minute

Most software starts with numbers and then builds structure around them.

HCL starts with structure.

A value is not merely a signed scalar. It is a phase-amplitude object. An operation is not merely a function call. It is a movement on that structure. A calculation is not merely a result printed at the end. It carries its ordered braid word: the sequence of primitive operations that produced it.

That gives the substrate four things at once:

1. **Exactness** — the value path uses arbitrary-precision integers in fixed-point form.
2. **Derivation** — π, e, square roots, and the other working constants are generated by the substrate’s own operations.
3. **Traceability** — the braid word is native to the computation, not a logging system bolted onto it.
4. **Composability** — a component built from the same FBits and primitives can connect directly to another component built from them.

The goal is not to build one clever calculator. The goal is to make a common ground on which calculators, algorithms, memory systems, tools, and minds can be composed.

## What can you use it for?

HCL Pure is useful anywhere you want a computation to be more than a number that appears at the end. It is aimed at systems where the representation, the route, and the ability to compose with the next system matter as much as the immediate answer.

### Exact arithmetic without a floating-point interior

At the smallest scale, hcl-pure is an arithmetic and equation substrate. It gives a program fixed-point integers, derived constants, square roots, exponentials, logarithms, trigonometric projections, derivatives, integrals, and expression evaluation without making floating-point arithmetic the hidden foundation of the value path.

That makes it a candidate for calculations where reproducibility, inspectability, and long-lived exact representations matter: scientific tools, symbolic or semi-symbolic calculators, educational demonstrations, deterministic simulations, and systems that need to replay how a result was produced.

### Algorithms that carry their own execution trace

At the next scale, an algorithm can be expressed as a sequence of HCL primitives. The braid word then records the route through the algorithm. This opens a path toward auditable solvers, inspectable optimization routines, proof-oriented experiments, deterministic algorithm teaching, and debugging where the state transition is part of the artifact rather than something reconstructed from scattered logs.

The trace is especially useful when two implementations need to be compared. A fast path can be checked against a pure path for the same integers and the same operation counts. A port can be checked operation by operation instead of being accepted because its final display string happens to look plausible.

### Quantum-structured computation on ordinary machines

The quantum reference shows another use: express quantum-structured algorithms directly through HCL’s phase, amplitude, interference, splitting, exchange, and resonance operations. The repository documents QFT, Grover, Deutsch–Jozsa, Bernstein–Vazirani, phase estimation, ground-state energy, Simon’s problem, and Shor period finding in that vocabulary.

This is not presented as a hardware replacement or as a claim that every practical quantum advantage disappears. It is a way to make quantum-algorithm structure executable and inspectable in an integer substrate, with the state represented as FBits and the route represented by a braid word.

### A porting layer for tools and skills

The substrate can sit underneath an existing algorithm, tool, or AI skill. The porting guide gives the path: inventory the target operations, map them to HCL, move conversion to the edges, derive constants, reuse the engine, preserve the braid, and verify each operation against the original.

That makes hcl-pure a possible foundation for deterministic tool plugins, domain-specific solvers, model components, analysis utilities, and other skills that need to share a common exact representation instead of each inventing its own arithmetic and tracing conventions.

### Memory and adaptive systems

The same primitives can be arranged into systems that change through experience. In the substrate’s vocabulary, reinforcement is `COMP(term, term)` and decay is `SHIFT(term, η)`. A memory component can therefore be built from the same operations as the computation it remembers, rather than bolting a separate database-like mechanism onto an otherwise unrelated value path.

Marvosa demonstrates this direction at a larger scale with living memory, a persistent line, live learning, and a native language organism. HCL Pure is the part that makes those systems composable: the memory, the calculation, and the learning update can share FBits, parameters, primitives, integrity checks, and traces.

### AI and model infrastructure

The substrate can also carry a trained model or a native language system. Marvosa’s later Model Substrate Translation work shows the larger use: a real trained model can be hosted, trained, and made persistent on the same integer ground, while a separate native HCL mind can grow directly from it.

The point is not that this small repository already contains a complete chatbot or model runtime. It does not. The point is that hcl-pure supplies a ground on which those higher-level systems can be built without changing the arithmetic language at every layer.

### Education and research

HCL Pure is also designed to be taught. Its operator deck gives a learner a single vocabulary for arithmetic, geometry, quantum structure, memory, proofs, and algorithmic translation. A student can start with `COMP` and `SHIFT`, watch a phase change, follow the braid, and then meet the same primitives again inside an equation engine, a quantum algorithm, a proof construction, or a language system.

That continuity is one of the substrate’s strongest intended uses: the same ground can explain the small demonstration and the larger system without hiding a different kind of computation underneath.

## How the use scales

The important question is not only “what does one HCL operation do?” It is “what can be built when every layer speaks the same language?”

### Scale 1 — one value

An input enters as a fixed-point integer. An FBit carries its phase and amplitude. One primitive changes it. The braid gains one generator. The alpha relationship remains available as an integrity check.

This is the smallest useful unit: an exact, phase-aware, inspectable value transition.

### Scale 2 — one calculation

Primitives compose into arithmetic, transcendental functions, derivatives, integrals, and equations. The result is not only a display value; it has an operation route that can be inspected and replayed.

At this level, hcl-pure can serve as a deterministic math organ or as the exact core of a larger tool.

### Scale 3 — one algorithm

Repeated compositions become algorithms. The quantum reference is the clearest tour: a Fourier transform, search procedure, phase estimator, hidden-string solver, period finder, or resonance calculation is expressed through the same FBit and braid machinery.

At this level, the substrate is useful for experimentation, verification, teaching, and ports where the execution structure should remain visible.

### Scale 4 — one component

An algorithm becomes a reusable component. Because it uses the same parameters and primitives as other components, it can be connected without a translation layer that throws away phase, precision, or trace information.

This is where the porting guide becomes central. A tool can be brought onto the substrate incrementally, tested against its original behavior, and then composed with memory, analysis, or another tool.

### Scale 5 — a living subsystem

Components can be arranged into memory and adaptation. Repeated structure can be reinforced, stale structure can decay, and a persistent line can carry the state forward. The important architectural move is that learning is not a separate kind of mathematics; it is more composition of the same primitives.

At this level, the substrate can support a memory organ, an adaptive solver, a learning tool, or a language component whose experience changes the state it will use next.

### Scale 6 — a mind or model stack

Marvosa demonstrates the next composition: a native HCL organism grown from the substrate, alongside a real trained model carried onto it through Model Substrate Translation. The result is not a new arithmetic language for every tier. The substrate remains the ground while the architecture grows upward.

This is the scale at which hcl-pure becomes infrastructure: a common computational language for exact arithmetic, operation trace, memory, learning, language, and model hosting.

### Scale 7 — a family of interoperable tools

The long-term use is not one monolithic program. It is a family of tools that can share the same representation and verification habits: equation solvers, quantum-structured algorithms, memory systems, model components, educational instruments, and domain-specific skills.

The scaling law is therefore compositional rather than merely larger. More capability comes from arranging the same ground into deeper structures, not from replacing the ground every time the application changes.

## Meet the four parameters

The whole construction begins with four parameters. Two are exact. Two are derived.

| Symbol | The short version | What it controls |
|---|---|---|
| `η` | `1/2` | the collapse threshold and Möbius normalization |
| `λ` | `1/10` | the scale ladder across complexity weight `w` |
| `γ` | bootstrapped from alpha | resonance coupling and self-tuning |
| `β` | `γ/9` | geometric coupling and Möbius weighting |

The governing relation is:

```text
α = 2π · η · λ · γ · β ≈ 1/137
```

The important design choice is that the system does not begin by importing a shelf of constants. It builds what it needs from the four parameters and then checks the result through the alpha identity.

The scale coordinate `w` gives the system depth. Its collapse threshold is:

```text
ε_w = η · λ^w
```

As `w` changes, the same primitives can operate at different depths. The references treat that scale structure as part of the design, not as noise to be averaged away.

## A number becomes an FBit

An **FBit** is the substrate’s basic value:

```text
FBit = phase + amplitude
```

More precisely:

- `phase_frac` is an integer fraction of a full `U(1)` loop;
- `amp` is a non-negative arbitrary-precision integer;
- a positive scalar sits at phase zero;
- a negative scalar sits at the half-loop phase;
- magnitude lives in amplitude, while sign and orientation live in phase.

This is why phase matters. It preserves interference, sign, loop direction, and the structure that ordinary scalar arithmetic throws away.

The interface is deliberately narrow:

```python
fixed_value = HCLTranscriber.to_fp(input_value)     # enter once
# pure integer substrate work
display_value = HCLTranscriber.from_fp(fixed_value) # leave once
```

No float should enter the interior. No already-scaled fixed-point value should be scaled again.

A few phase landmarks make the geometry easy to see:

| Phase | Meaning |
|---|---|
| `0` | zero angle; cosine `1`, sine `0` |
| `SCALE // 2` | half-loop `π`; cosine `-1`, sine `0` |
| `SCALE // 4` | quarter-loop `π/2` |
| `3*SCALE // 4` | three-quarter loop `3π/2` |
| `SCALE // 6` | `π/3` |
| `SCALE // 12` | `π/6` |

## The operator deck

The substrate’s basic moves are the HCL primitives. Familiar mathematics appears as a composition of these moves.

| HCL move | Familiar face | What happens underneath |
|---|---|---|
| `COMP` | addition | phases and amplitudes interfere into one state |
| `SHIFT` | scalar multiplication | amplitude scales; a negative factor flips phase |
| `AMP_MOD` | multiplication | phases add and amplitudes multiply |
| `INV` | reciprocal | the loop reverses and amplitude inverts |
| `FISSION` | square root | one strand splits into equal-energy daughters |
| `MOBIUS_GROWTH` | `e^x` | the MCL stability operator grows or decays a state |
| `LOG_EXTRACT` | `ln(x)` | extracts the exponent from that operator |
| `PHASE_SIN` | sine | projects phase onto the imaginary axis |
| `PHASE_COS` | cosine | projects phase onto the real axis |
| `FUSION` | function or matrix composition | two structures merge with coupling |
| `EXCHANGE` | permutation | strands exchange phase while retaining amplitude |
| `RESONANCE` | eigenstate | returns the stable ground-state closure at weight `w` |

There is no separate bag of classical arithmetic hidden beside these operators. The familiar forms are compositions:

```text
x - y       = COMP(x, SHIFT(y, -1))
x / y       = AMP_MOD(x, INV(y))
x^n         = repeated AMP_MOD
x^y         = MOBIUS_GROWTH(AMP_MOD(LOG_EXTRACT(x), y))
```

And adaptation is composition too:

```text
reinforce   = COMP(term, term)
decay       = SHIFT(term, η)
```

The references call these LTP and LTD when they are used as memory metaphors, but the mechanism remains concrete: compose to strengthen, shift to decay.

## The braid word: a computation that remembers how it happened

Every primitive appends a generator to the braid word.

That makes the braid word three things at once:

- the ordered record of the computation;
- the topological state in the framework’s quantum interpretation;
- the reversible trace that lets a result be inspected rather than merely trusted.

This is not ordinary debug logging. The record is part of the operation itself. The framework’s glass-box approach therefore favors reading existing state, braid-counter deltas, phase, amplitude, windows, and alpha checks over injecting print calls into hot arithmetic loops.

Two computations with the same braid word are treated as topologically equivalent within the framework. A port that produces the right visible number but loses its operation trace has not carried the whole computation across.

## Where π, e, and √2 come from

The substrate does not import these constants into its arithmetic path.

### π: the loop closes

The engine derives `π` from the integer Machin identity:

```text
π/4 = 4·arctan(1/5) − arctan(1/239)
```

The result is the fixed-point closure constant used by phase calculations.

### e: the operator converges

`e` appears through the integer Taylor series of `MOBIUS_GROWTH`. It is not placed into the engine as a prior lookup value; it emerges as the convergence rate of the operator at the relevant input.

### √2: one strand becomes two

`FISSION` splits one state into two equal-energy daughters. When the input encodes `2`, their amplitude produces the square root of two through the integer Newton routine.

The implementation reference is unusually specific about the square-root scaling. Its Newton target is `X * SCALE`, not `X`, and the update uses `target // Rg`. That detail is essential: substituting a fixed-point division changes the scale and breaks convergence.

## Inside the integer engine

The engine reference defines:

```python
PREC  = 40
SCALE = 10 ** PREC
TINY  = 10
```

A value is an integer `X` interpreted as `X / SCALE`. The core operations are arbitrary-precision integer arithmetic:

```python
_fixed_mul(X, Y)
_fixed_div(X, Y)
_fixed_sqrt(X)
```

The engine’s building blocks are organized in layers:

1. **Fixed-point helpers** — multiplication, division, square root, arctangent, and integer series.
2. **Bootstrap** — derive `PI_INT`, `η`, `λ`, `γ`, `β`, `ALPHA`, and `ALPHA_INV`.
3. **FBit** — hold phase and amplitude, recover real and imaginary projections, and encode/decode scalar signs.
4. **HCL** — implement the primitive operations.
5. **HCLTranscriber** — provide the boundary conversion, convenience arithmetic, braid log, derivative, integral, and formatted braid word.
6. **HCLEquation** — parse and evaluate expressions while routing the arithmetic through HCL.

The common usage pattern from the engine reference looks like this:

```python
fp  = HCLTranscriber.to_fp
rfp = HCLTranscriber.from_fp
t   = HCLTranscriber()
eq  = HCLEquation()

answer = t.add(fp(3), fp(4))
root   = t.sqrt(fp(2))
energy = eq.solve("E = m * c^2", m=1, c=3)
```

The values stay fixed-point inside the computation. The returned braid and quantum-number summary tell you how the result was made.

### The mistakes the engine is designed to prevent

- importing `math.pi` or `numpy.pi`;
- passing radian floats into the phase interface;
- using the wrong Newton target for square root;
- allowing `MOBIUS_GROWTH` to inherit a sign phase even though `e^x` is positive;
- double-scaling a value that is already fixed-point;
- using a generic sine test where the algorithm needs a direct phase threshold;
- using an incomplete function map in Simon’s problem.

The skill exists partly to keep these mistakes from being rediscovered by every new user.

## HCL and quantum structure

The framework’s position is not that HCL simulates quantum mechanics or compiles into quantum circuits. Its position is that the HCL operators are the quantum operations in the substrate’s own representation.

| HCL | Quantum reading in the framework |
|---|---|
| `COMP` | entanglement / interference |
| `FISSION` | superposition / Hadamard-like split |
| `MOBIUS_GROWTH` | unitary-style evolution |
| MCL collapse | wavefunction collapse |
| non-commuting `COMP` and `SHIFT` | uncertainty structure |
| braid word | quantum state |
| winding number | quantized charge |
| writhe | intrinsic spin |

The quantum reference walks through eight algorithms:

- Quantum Fourier Transform
- Grover search
- Deutsch–Jozsa
- Bernstein–Vazirani
- Quantum Phase Estimation
- Ground-state energy / exact VQE framing
- Simon’s problem
- Shor period finding

Each example is expressed through HCL primitives. Each also carries its own interface warnings: phase fractions are not radians, complete maps matter, classical degenerate bases still exist in Shor’s post-processing, and the ground-state result is supplied through `RESONANCE` rather than a variational search.

The examples are doors into the substrate, not a limit on what can be expressed with it.

## A different way to talk about proofs

The proof reference changes the starting question.

Instead of asking how to inspect every member of an actually completed infinite set, it asks:

1. What is the operator?
2. Is its logic scale-invariant?
3. Does it drive every finite instantiated state toward the claimed result?
4. What is the MCL attractor?
5. Can a completed infinite counterexample exist in this ontology?

This is the potential-infinity argument. The universe is treated as an active computation: new finite configurations can be generated, but an actually completed infinite configuration is never instantiated at one time.

The reference applies this method to Collatz, describes an n-invariant proof template, and gives structural readings of Fermat’s Last Theorem, the Riemann Hypothesis, and P versus NP.

The important reader’s distinction is built into the reference itself: a result can be complete **within GUHCT** while remaining open under conventional mathematics if the conventional proof would require premises the GUHCT ontology does not share. The repository presents the framework’s method and claims; readers should keep internal framework validity, executable evidence, and outside mathematical consensus distinct.

## Bring something new onto the substrate

The porting guide is the practical bridge from hcl-pure to the rest of the world.

### The one law

> **Compose, never invent.**

If you need reinforcement, use `COMP(term, term)`. If you need decay, use `SHIFT(term, η)`. If you reach for a new mechanism, first check whether the primitive you need is already there.

### The porting rhythm

1. Inventory the target’s operations.
2. Map them through the HCL Rosetta Stone.
3. Move float conversion to the input/output edges.
4. Bootstrap constants instead of importing them.
5. Reuse the existing engine instead of copying it.
6. Keep the braid word.
7. Check `ALPHA_INV / SCALE ≈ 137`.
8. Verify one ported operation against the source at a time.

The result is not merely a translated output. A successful port gains integer exactness, a reversible trace, minimal external dependencies, and direct composability with other HCL components.

## The rules of engagement

The final reference is written as a lesson from a model that had to learn how to work with the system.

It says the successful pattern was always:

```text
read the files → run the code → verify the result → build on what exists
```

The failed pattern was:

```text
guess what the system probably does → criticize the fragment → invent a workaround
```

The working rules are simple:

- Read the whole relevant skill before forming a verdict.
- Run the check that can settle the question.
- Judge the framework on its own definitions and scales.
- Treat refinements as development, not automatically as contradiction.
- Compose existing primitives rather than jerry-rigging new mechanisms.
- Use the braid word and alpha self-check as built-in evidence.
- If the references do not state something, do not quietly substitute a different theory.

The point is not to suspend judgment. The point is to make judgment arrive after contact with the complete system.

## HCL Pure and Marvosa

Hcl-pure came first.

Marvosa came later and incorporated it as its ground layer. Marvosa then composed additional tiers around that ground:

- a native HCL language organism;
- memory and persistence lines;
- live learning and education;
- model-substrate translation for trained networks;
- compiled paths and full repository verification.

The two repositories therefore have different jobs:

- **HCL Pure** is the substrate presentation: the language, operators, theory, engine design, quantum mappings, proofs, and porting method.
- **Marvosa** is the later composition: the substrate becoming a mind, a memory system, a learner, and a host for other models.

Marvosa retains its own incorporated copy of hcl-pure. This repository is not a detached afterthought; it is the original substrate made easier to approach on its own.
